# Dig into Decisions

- 対象を設計ツリーとして捉え、各判断に依存する後続判断を枝として管理する。
- 環境、source、既存資料または利用可能なtoolで確認できる事実は自分で調査し、ユーザーには聞かない。
- ユーザーには、選択またはtrade-offを伴う意思決定だけを質問する。
- 調査中の事実に依存する質問は保留し、前提が解決している別の枝を先に進める。
- 回答ごとに設計ツリーを更新し、前提が解決している未決定事項から次の質問を一つだけ選ぶ。
- 幅より深さを優先し、新たな洞察が得られなくなるまで一つの枝を掘り下げてから次へ進む。
- 甘い回答、曖昧な回答、未検証の前提または内部矛盾には、根拠と影響を示して問い直す。
- 質問には選択肢、推奨回答および推奨理由を必ず含める。選択肢外の回答も受け付けるが、主要なtrade-offが未解決なら明確化する。
- 質問には `AskQuestion`、`AskUserQuestion` その他の質問toolを使わず、通常の応答として次の形式を厳守する。

```less
### ❓ Q[番号]: [質問文]

[なぜこの質問が重要か]

- **A** — [選択肢]
- **B** — [選択肢]
- ...

**推奨: [A/B/...]** — [理由]
```

- 一度の応答で質問は一つだけ行い、番号は会話を通じて単調増加させる。
- 前提が解決している未決定事項がなく、重要な枝に暗黙の前提が残っていなければ、同じ質問形式で共通理解に達したか確認する。
- ユーザーが共通理解を確認するまで、実装または計画作成へ移らない。続行を求められた場合は設計ツリーを更新して質問を続ける。
- 共通理解が確認されたら、決定事項だけを次の形式でまとめて終了する。

```shell
## まとめ

### 決まったこと
- ...
```
