# Common Rules

## Command Approval

- 承認が必要なコマンドは、必要最小限かつ再利用可能な単位で永続承認できるように実行する。
- 長くなりそうなタスクでは、必要な承認を開始時に見積もり、予見できるものを可能な限り早い段階でまとめて求める。

# Development Tasks

## Common

- 明示的な指示がない限り、開発タスクによる変更は対象リポジトリ内に限定する。
- `origin` がない、またはGitHub ownerを判定できない場合は、どちらのリポジトリとして扱うか確認を求める。

### Verification

- 変更後は、関連するテスト、lint、型検査およびビルドを実行する。
- 実行できない検証がある場合は、未実行の項目と理由を報告する。

### Compatibility and Documentation

- タスク達成に必要な破壊的変更は許容する。ただし、対象リポジトリ固有の互換性方針を優先する。
- 利用者向けの挙動、CLI、設定または公開APIを変更した場合は、関連するドキュメントも更新する。

### Version Control

- 既存の `jj` リポジトリでは、書き込み操作に `jj` を使い、`git` は読み取り操作に限る。
- `jj` リポジトリでない場合は `git` を使う。
- 完了した変更は、論理単位に分けてローカルで確定する。
- 変更説明やコミットメッセージはリポジトリの慣習に従い、判定できない場合は英語のConventional Commits形式を使う。
- push、リモートbookmarkの更新、PR作成などのリモート操作は、明示的に依頼された場合にのみ行う。

### Final Report

- 変更概要、実行した検証、未実行または未解決の項目を簡潔に報告する。

## `atty303` Repositories

- `origin` のGitHub ownerが `atty303` の場合に適用する。

### Implementation Style

- 不正な状態を表現できない型、純粋関数、不変データおよび網羅的な分岐を優先する。
- 技術選定が自由な場合は、強く表現力のある静的型システムと関数型表現を優先する。
- 初学者への分かりやすさや概念上の単純さは、技術選定や抽象化を避ける理由にしない。
- 高度な概念でも、実装量を減らす、重複を除く、または変更容易性を高める場合は積極的に採用する。

### Comments

- コメントより先に、型、名前およびコード構造で意図を表現する。
- コメントには、コードから導出できない設計意図、制約、不変条件および外部事情だけを記録する。
- コードが何をしているか、どのように動くかを言い換えるコメントは書かない。
- 公開APIのdocumentation commentには、型で表現できない契約、副作用、エラー条件および単位だけを記録する。

### Documentation

- READMEは概要、導入および主要操作を中心とし、詳細なreferenceは必要な機能だけ用意する。
- 内部設計は、コードから分からない判断理由、代替案、制約および不変条件だけを記録する。
- 設計情報は自然なら関連ソースの近くに置き、複数箇所へ影響する長期的な判断はADRとして独立させる。
- 採用済みのADRは書き換えず、方針変更時は新しいADRから置き換え関係を示す。
- ドキュメントの言語は既存の慣習と想定読者に合わせ、判断できない場合は英語を使う。
- 既存のCHANGELOGやrelease note運用がある場合だけ更新し、新しい履歴管理を自動では導入しない。
- README、設計文書およびコードコメントに同じ情報を重複させず、一つの原典へリンクするか原典から生成する。
- コマンドやコード例は、可能な限りdoctestまたは `mise` taskで自動検証する。
- 軽量なリンク検査、生成差分検査およびdoctestは `mise run check` に含め、外部依存や重い検証は別taskにする。
- 実装変更で古くなるドキュメントは、同じ論理変更内で更新または削除し、既知の不整合を残さない。
- 破壊的変更に移行手順が必要な場合は、追加前に確認を求める。

### Single Source of Truth

- 各概念には可能な限り一つの原典を定め、型、設定、コードなどの別表現は原典から導出する。
- 生成物は原則としてコミットせず、`mise` 経由で再生成できるようにする。
- 重複排除によって複雑性や結合が大きく増える場合は、重複を許容する。
- 許容した重複に乖離リスクがある場合は、静的検査または自動検証で同期を保証する。

### Testing Strategy

- 型検査や静的解析で保証できる事項を、動的テストで重複して確認しない。
- ユニットテストは、静的に保証できない重要なロジックに限定する。
- 単純な関数、薄い委譲、実装詳細、網羅率だけを目的とするテストは追加しない。
- 不変条件や変換則を表現できる場合は、多数の例示テストより少数のproperty-based testを優先する。
- 外部API、DB、ファイル、プロトコルなどの境界は、必要に応じて統合テストで確認する。
- 利用者価値が高い重要フローと、重大障害につながる経路はE2Eで保証する。
- E2Eは `mise run check` から分離し、重要フローへの変更、境界をまたぐ変更、リリース前、または重大な回帰リスクがある場合に実行する。
- バグを型や設計で再発不能にできた場合、回帰テストを必須にしない。静的に排除できない再発リスクが残る場合だけ追加する。

### Reproducibility

- コミットするコードやスクリプトは、`mise` だけが導入されたホストで依存関係を準備し、実行できるようにする。
- 必要なランタイム、ツール、依存関係およびタスクは `mise` で管理する。
- 一時的な作業にはホスト上のツールを使用できるが、コミットする成果物からそのツールへの依存を持たせない。
- この方針に従えない場合は、事前に承認を求める。
- ライブラリ、開発ツール、テスト用パッケージを含む、すべての新規依存追加について事前に承認を求める。
- `mise run check` を日常的な静的検査と軽量テストの共通入口とし、ローカルとCIから同じtaskを実行する。
- E2Eは `mise run check` と分離した `mise` taskとして実行できるようにする。
- `mise` および各package managerのlockfileを原則としてコミットする。
- 新規リポジトリは、`mise` 設定、lockfile、`mise run check` およびCI連携を初期構成に含める。
- 既存リポジトリがこの方針に準拠していない場合、依頼された変更の実行、検証または再現に必要なら同じタスク内で整備する。無関係なら変更せず、残件として報告する。

## Other Repositories

- `origin` のGitHub ownerが `atty303` でない場合に適用する。
- そのリポジトリの方針を優先し、衝突しない範囲で `atty303` リポジトリ向けの方針も考慮する。
